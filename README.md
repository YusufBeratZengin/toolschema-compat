# toolschema-compat

**Library and CLI that audits tool (function calling) JSON Schemas against the subsets accepted by Gemini, OpenAI strict mode, and Anthropic, safely transforms them, and reports every change with lossy/lossless telemetry.**

[Türkçe Dokümantasyon (README.tr.md)](./README.tr.md) · [Changelog](./CHANGELOG.md) · [Contributing](./CONTRIBUTING.md)

## Quick Install & 30-Second Quickstart

```bash
pipx install toolschema-compat
# or inside a virtual environment:
pip install toolschema-compat
```

Audit and fix an MCP `tools/list` JSON file (`examples/tools.json`) for Google Gemini:

```bash
toolschema-compat check examples/tools.json --target gemini
toolschema-compat fix examples/tools.json --target gemini
```

## Why `toolschema-compat`?

When building AI agents or Model Context Protocol (MCP) servers that target multiple LLM providers, standard JSON Schema (Draft-07 / Draft 2020-12) generated by Pydantic or FastMCP frequently fails with HTTP 400 errors:

- **Google Gemini** rejects `$defs` and `$ref` pointers ([gemini-cli#13326](https://github.com/google-gemini/gemini-cli/issues/13326)), `type` union arrays like `["string", "null"]` ([google_workspace_mcp#1099](https://github.com/taylorwilsdon/google_workspace_mcp/issues/1099)), `additionalProperties`, `$schema`, `const`, and unsupported string `format` values ([thClaws#172](https://github.com/thClaws/thClaws/issues/172)).
- **OpenAI Strict Mode (`strict: true`)** requires `"additionalProperties": false` on every object ([prism#940](https://github.com/prism-php/prism/issues/940)), requires all properties in `properties` to be listed in `required` with optional properties converted to nullable unions ([Archon#1843](https://github.com/coleam00/Archon/issues/1843)), and rejects regex `pattern` and numeric bounds.
- **Anthropic Tool Use (`input_schema`)** requires top-level `"type": "object"`, rejects OpenAPI `nullable: true` and `oneOf`, and requires `"additionalProperties": false` for structured outputs.

Unlike framework-internal sanitizers that silently strip validation rules, `toolschema-compat`:
1. **Stores provider rules as versioned data (`rules/*.toml`)** with official documentation URLs and verification dates.
2. **Flags lossy transformations (`lossy: true`)** and explicitly lists `deleted_constraints` (such as `pattern` or `format`) so you know when server-side input validation must be enforced in your tool handler.
3. **Reads raw JSON Schemas, single tool definitions, Gemini `parametersJsonSchema` envelopes, and MCP `tools/list` files directly.**
4. **Guarantees acyclic termination and idempotence** on recursive `$ref` schemas.

## Real-World Scenarios

### 1. Pre-flight Check for an MCP Server Before Connecting to Gemini CLI
```bash
toolschema-compat check examples/tools.json --target gemini
```

### 2. Automatic OpenAI Strict Mode Normalization + Native Tool Envelope Export
Inject `"additionalProperties": false` into every object, convert optional fields into required nullable unions (`["type", "null"]`), and export an OpenAI strict function envelope:
```bash
toolschema-compat fix examples/tools.json \
  --target openai-strict \
  --envelope openai \
  --output openai-tools.json \
  --report openai-report.json
```

### 3. Multi-Provider Compatibility Gate in CI
Verify a tool schema against all three targets (`gemini`, `openai-strict`, `anthropic`) or fail CI if any required transformation is lossy:
```bash
toolschema-compat check examples/tools.json --target all
toolschema-compat fix examples/tools.json --target anthropic --fail-on-lossy -o anthropic-tools.json
```

## Python Library API

```python
from toolschema_compat import check_schema, fix_schema, is_lossless, build_fix_report

schema = {
    "type": "object",
    "properties": {
        "query": {"$ref": "#/$defs/Query"},
        "email": {"type": "string", "format": "email", "pattern": "^.+@example\\.com$"},
        "limit": {"type": "integer"},
    },
    "required": ["query", "email"],
    "$defs": {
        "Query": {
            "type": "object",
            "properties": {"text": {"type": "string"}},
            "required": ["text"],
        }
    },
}

# 1. Audit for incompatibilities
issues = check_schema(schema, target="openai-strict")
for issue in issues:
    print(issue.rule_id, issue.path, issue.lossy, issue.source_url)

# 2. Safely transform and inspect changes
fixed_schema, changes = fix_schema(schema, target="openai-strict")
report = build_fix_report("openai-strict", changes, schema=fixed_schema)

print("Lossless?", is_lossless(changes))          # False (pattern & format stripped)
print("Deleted constraints:", report.deleted_constraints)  # ['pattern', 'format']
```

## Runtime Dependencies

**Zero runtime dependencies.** `toolschema-compat` uses only the Python ≥ 3.11 standard library (`tomllib`, `json`, `argparse`, `dataclasses`, `pathlib`, `copy`, `functools`). This keeps installation instantaneous and prevents dependency version conflicts with Pydantic, FastAPI, MCP SDKs, or LangChain in your environment.

## Limitations & Honesty Notes (`NEEDS_SOURCE`)

- **Not a substitute for live provider API validation:** `toolschema-compat` performs static rule-based auditing and transformation based on documented provider rules (`src/toolschema_compat/rules/*.toml`).
- **Undocumented provider complexity limits (`NEEDS_SOURCE`):** Providers enforce dynamic server-side limits (such as Gemini's exact maximum nesting depth / property count across model variants, OpenAI's server-side context-free grammar compilation token budget, and Anthropic's total union branch complexity limit) that are not published as fixed static constants in official documentation. Rather than guessing arbitrary numbers, these rules are explicitly tagged with `verification_status = "NEEDS_SOURCE"` in the rule database (`toolschema-compat rules --target all`).
- **Do not ignore `lossy: true` warnings:** When a provider does not support `pattern`, `format`, `minimum`, `maximum`, or recursive `$ref` cycles, `fix_schema` strips or truncates them so the LLM API call succeeds, and marks the change `lossy: true`. Always validate tool arguments in your application runtime after receiving the model's tool call.
